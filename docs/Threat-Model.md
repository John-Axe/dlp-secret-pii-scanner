# Threat Model

Trust boundaries this codebase already implements — some deliberately, some
as a byproduct of the zero-runtime-dependency design — written down
explicitly rather than left implicit in scattered code comments. Every
specific claim below was verified against the current source
(`src/dlp/`) while writing this, not assumed from memory.

## What this tool trusts

- **The source tree it's pointed at.** `dlp-scan` reads file bytes and runs
  regex/entropy matching against them — it never executes, imports, or
  evaluates anything from a scanned file. There's no `eval`, `exec`,
  `pickle.loads`, or dynamic import anywhere in `src/dlp/` (verified via
  `grep` across the package, not assumed) — the only way a scanned file's
  *content* can affect this tool's behavior is by being matched against a
  detector pattern or fed through the entropy calculation, both pure,
  side-effect-free functions over the bytes.
- **The local git binary and repository state**, for `--diff-only`
  (`diff.changed_files` shells out to `git diff --name-only`). If the local
  git state is manipulated, `--diff-only` could miss files a "real" diff
  would include — out of scope for this tool to defend against; it trusts
  its environment's git the same way any CLI tool trusts its environment's
  core utilities.
- **`GITHUB_TOKEN`, when present**, for exactly one purpose: authenticating
  PR-comment POST requests in `github_pr.py`. Read from the environment
  once, used only to build the `Authorization` header, never logged, never
  included in any finding output, never written to disk.

## What this tool does NOT trust

- **The content of scanned files, as adversarial input, not just as typical
  source code.** A file could be deliberately crafted to try to make the
  scanner hang (a ReDoS-style regex attack) or crash. Two independent
  defenses exist for this: `fuzz/fuzz_scanner.py` (atheris, exercises every
  detector against arbitrary generated bytes in CI) and
  `tests/test_performance_smoke.py` (a CI-gated wall-time ceiling
  specifically targeting catastrophic backtracking — see that file's own
  docstring). Neither *proves* no such input exists; both make one
  meaningfully harder to introduce and ship undetected.
- **The GitHub API's response body**, in `github_pr.py`. A successful
  response is parsed as JSON and only its `id` field is read
  (`body.get("id")`) — nothing else in the response is trusted or acted
  on. An unexpected/malformed response raises rather than being silently
  accepted.
- **`--base-ref`'s value, as a potential injection vector** — it isn't one.
  The only subprocess call in this codebase
  (`subprocess.run(["git", "diff", ...], ...)` in `diff.py`) passes
  arguments as a list, never `shell=True` and never string-interpolated
  into a shell command (confirmed via `grep -rn "shell=True" src/dlp/` —
  no matches, anywhere). A malicious or malformed ref value can make the
  underlying `git diff` command fail; the `except` clause around it treats
  that identically to "nothing changed" (returns `[]`), not as an error
  condition to propagate — there's no path from an attacker-influenced ref
  string to command execution.

## Output as an attack surface, not just input

- **Finding previews, everywhere** (`detectors.redact`): never the full
  matched secret, only a few characters at each end (2 for short/sensitive
  values like SSNs, 4 otherwise) with everything else starred out — and
  every backtick already replaced with `*` at this single point, before the
  preview is ever attached to a `Finding`. This means every output sink —
  table, JSON, SARIF, PR comments, `findings.jsonl` — carries the same
  bounded, non-reconstructable preview, not the underlying credential.
- **PR review comment bodies specifically** (`github_pr.build_comment_payload`)
  re-apply the same backtick substitution a second time
  (`safe_redacted = finding.redacted.replace("`", "*")`) directly on the
  value going into a Markdown comment body — redundant with `redact()`'s
  own stripping today, but a deliberate belt-and-suspenders choice for the
  one sink where a stray backtick has a real, specific consequence
  (breaking out of a Markdown code span and letting the rest of the
  comment render as arbitrary Markdown), not left to depend on a guarantee
  made by a different module three call-frames away.

## Supply chain

- **Zero runtime dependencies** (`dependencies = []` in `pyproject.toml`)
  is the largest single reduction in attack surface this project has: there
  is nothing to compromise in the dependency tree of the shipped package,
  because there is no dependency tree. See `shared_finding.py`'s docstring
  and the original engineering audit for this framed as a deliberate
  architectural choice, not an accident.
- **Dev dependencies** (`pytest`, `pytest-cov`, `hypothesis`, `atheris`,
  `ruff`, `mypy`) run in CI and local development only — never in the
  shipped, installed tool. Dependabot watches both the `pip` and
  `github-actions` ecosystems weekly (`.github/dependabot.yml`); every
  third-party GitHub Action is pinned to a full commit SHA with a version
  comment, not a mutable tag.
- **CI job permissions are least-privilege**, scoped per-job rather than
  repo-wide: `contents: read` by default, `pull-requests: write` and
  `security-events: write` only on the one job (`pr-scan.yml`) that
  actually needs them. See [`README.md`](../README.md#security) for the
  full list.

## Explicitly out of scope

- **Detecting that this tool itself has a vulnerability once installed** —
  covered by [`SECURITY.md`](../SECURITY.md)'s private disclosure process,
  not by this document.
- **Anything downstream of a finding being reported.** If `--format json`
  output (or `findings.jsonl`, or a SARIF file) is subsequently logged,
  stored, or transmitted insecurely by *another* system, that's outside
  this tool's boundary — the redaction guarantees above hold for what this
  tool produces, not for what happens to that output afterward.
- **Confirming a found credential is still live or was ever real.** See
  [`Limitations.md`](Limitations.md) — a threat-model document about what
  this tool defends against is a different question from what it claims to
  detect accurately, covered there instead.
